# Модуль «Калькуляторы»

Автономный экран с 20 калькуляторами (энергия, питание, тело, движение). Написан
как обычный модуль приложения: одна папка, один импорт, никаких сетевых вызовов.

## Структура

```
calculators/
├── index.ts                     # публичный API модуля
├── types.ts                     # CalculatorProfile, Gender, ActivityLevel, CalorieGoal
├── screens/CalculatorsScreen.tsx# точка входа (default export)
├── components/                  # карточка, диалог, форма, поля, профиль
├── contexts/ProfileContext.tsx  # личные данные: профиль хоста + правки пользователя
├── hooks/useDialogBehavior.ts   # ловушка фокуса, Escape, возврат фокуса
├── lib/                         # каталог, формулы, адаптер профиля, валидация,
│                                #   профильный кэш (profileStorage)
├── images/                      # 25 фирменных миниатюр .webp (20 плашек + 4 иконки секций + шапка), 0.47 МБ
├── styles/calculators.css       # scoped-стили (.calc-*), без глобальных правил
└── __tests__/                   # 60 тестов (математика, адаптер, формы, экран, кэш)
```

## Зависимости

`react` (19) и `lucide-react` — уже есть в приложении; иконки lucide остались
только на служебных элементах (закрыть, стрелка), в плашках их заменили
миниатюры. Styling — классы Tailwind, как в остальных экранах. Больше внешних
зависимостей у модуля нет: миниатюры подключаются статическими
`import thumb from "../images/1.webp"`, их типизирует `vite/client`
(в `tsconfig.json` приложения он уже подключён через `"types"`).

## Дизайн-контракт экрана (360px)

Модуль проектируется под Telegram WebView: базовая ширина 360px, капсула
приложения до 440px. Проверенные значения, от которых не надо отходить:

| Элемент | Значение |
|---|---|
| фон экрана | `#FFFFFF` |
| плашка | высота 49px, радиус 18px, `padding: 3px 14px 3px 8px`, зазор 8px |
| рамка и тень плашки | `border: 1.5px solid #FFFFFF` + `0 4px 14px rgba(0,0,0,.05), 0 1px 3px rgba(0,0,0,.03)` — карточка «парит» над белым холстом |
| миниатюра | 40×40px, `object-contain`, `alt=""` (смысл несёт соседний текст); исходники — 192px по длинной стороне, их хватает на 3× DPR (замер отклонений ниже) |
| название | 14px / 600 / `#1E293B` / `line-height 1.2`, одна строка, truncate |
| пояснение | 11.5px / 400 / `#64748B` / `line-height 1.2`, одна строка, truncate |
| подзаголовок секции | иконка 24×24 + «0N · НАЗВАНИЕ», 12px / 700 / uppercase / `letter-spacing .05em`, цвет `#B95D47` `#406D4E` `#6A4D8C` `#9B454B` |
| шапка экрана | фирменная пиктограмма `01.webp` 42×42, без плитки и рамки |
| прокрутка | только жестом/колесом: у экрана (`h-dvh overflow-y-auto`) и у тела диалога полоса прокрутки скрыта (`scrollbar-width: none` + `::-webkit-scrollbar{display:none}`), правил для `body` модуль не вводит |
| подвал | `padding-bottom: 24px`, дисклеймер 11px с отступом 12px от списка |
| тон плашки | свой пастельный фон **и** свой насыщенный акцент у каждой из 20 карточек — в `lib/calculatorCatalog.ts` (`tint` / `accent`) |

Высота плашки не задаётся напрямую: 40px миниатюры + 3+3px по вертикали +
1.5×2px рамки дают 49px, и тот же расчёт держит ряд ровным при любом тексте.

### Акцент внутри диалога

`CalculatorModal` кладёт акцент открытого калькулятора на контейнер диалога как
CSS-переменные `--calc-accent`, `--calc-accent-soft`, `--calc-accent-ring`
(нейтраль значения по умолчанию — в `styles/calculators.css`, на `.calc-dialog`).
Кнопка «Готово», рамки фокуса и выбранные варианта в `RadioCards` читают их
через `bg-[color:var(--calc-accent)]` и т. п., поэтому акцент доезжает до
вложенных полей без пробрасывания пропсов. Модалка целиком белая
(`#FFFFFF`, радиус 24px), бежевых фонов внутри нет.

## Подключение

Модуль подключается одним файлом-окном — `host/CalculatorsWindow.tsx`. Он читает
`screen`, `setScreen` и `userProfile` из стора приложения и ничего в стор не
пишет: правки в диалоге «Мой профиль» остаются у модуля (см. «Личные данные и
кэш»).

1. **Файл окна** лежит в модуле: `src/modules/calculators/host/CalculatorsWindow.tsx`.
   Импорт `../../../store/useAppStore` совпадает с путём Bookport.

2. **Экран в сторе** — `src/store/useAppStore.ts`:

```ts
export type Screen =
  | ... | "calculators";
```

3. **Монтирование в `src/App.tsx`** — рядом с `<GlobalNotificationOverlay />`,
   вне `AnimatePresence`-цепочки экранов:

```tsx
import CalculatorsWindow from "./modules/calculators/host/CalculatorsWindow";

<>
  <GlobalNotificationOverlay />
  <CalculatorsWindow />
  <div className="w-full h-[100dvh] ...">   {/* оболочка приложения без изменений */}
```

и в цепочке ветвлений — ветка `null`, чтобы за окном не смонтировался
`MyDayScreen` со своими запросами:

```tsx
) : screen === "calculators" ? null : (
  <motion.div key="my-day-view" ...>
```

4. **Кнопка входа** — `src/components/BottomBar.tsx`, кнопка «Клуб»:

```tsx
onClick={() => setScreen("calculators")}
```

5. **tsconfig** — тестовых зависимостей (`vitest`, `@testing-library/react`) в
приложении нет, а тесты модуля лежат рядом с кодом:

```json
"exclude": ["src/modules/calculators/__tests__"]
```

Почему окно, а не ветка в цепочке: `CalculatorsScreen` занимает `h-dvh` и
прокручивает содержимое сам. Внутри капсулы приложения (`overflow-hidden`,
одна зона скролла) второй скролл ломает вёрстку, а `fixed`-подложка диалогов
попадает под transform-контейнер motion-обёрток. Окно монтируется на уровне
`App`, повторяет ширину капсулы (`max-w-[440px]`) и держит `contain-paint`,
чтобы подложка и модалка (у неё `max-w-[620px]`) на широких экранах оставались
в границах приложения. Предел растяжения задаёт само приложение.

Закрытие ведёт пользователя на главный экран приложения — `my-day`, тот же
приём, что `onBack`/`onNavigateHome` у остальных экранов. Экран модуля —
единственный контейнер для калькуляторов и личных данных: крестик и «Готово»
внутри диалогов закрывают только диалог и возвращают к списку.

## Контракт пропсов

```ts
interface CalculatorsScreenProps {
  profile?: HostProfile | null;                                  // вход: данные пользователя
  onProfileChange?: (profile: CalculatorProfile) => void;        // выход: правки пользователя
  onClose: () => void;                                           // закрытие — на главный экран ("my-day")
}
```

`HostProfile` принимает и канонические поля, и то, что обычно лежит в модели
пользователя (`gender`, `age`, `height`, `weight` — Bookport `UserProfile` подходит
как есть, включая строковые значения пола вроде `"женский"` и числа с запятой).
Давление из настроек (`systolic` / `diastolic`) превращается в `systolicMmHg` и
`diastolicMmHg` и показывается в личных данных рядом с пульсом. Всё, что не
проходит те же правила, что и ручной ввод в UI, отбрасывается: модуль **не
подставляет дефолты** и не считает «примерно». `activity` и `goal` у хоста могут
отсутствовать — тогда калькуляторы расхода просят заполнить их в карточке
личных данных.

`onProfileChange` получает полный профиль модуля, но только после реальной правки
пользователем: стартовые данные хоста обратно не отправляются. Окну Bookport
проп не передаётся — модуль остаётся только читателем данных приложения.

## Личные данные и кэш

Данные для расчётов приходят из Настройки → личные данные (проп `profile`).
Правки пользователя модуль хранит у себя: `lib/profileStorage`, ключ
`calculators.profile.v1` в `localStorage`.

- правка в плашке «Личные данные» или в любом калькуляторе переживает закрытие
  окна, перезагрузку и следующий запуск приложения;
- исходные значения — из профиля хоста, ручных «дефолтов» вида «женщина, 32,
  68 кг» в модуле нет;
- на каждое поле пишется пара `{value, hostValue}`: если после правки хост
  отдаёт другое значение, оно считается свежим и перекрывает кэш (пользователь
  поправил вес в Настройках — калькуляторы показывают его);
- поля, которых у хоста нет (обхваты, пульс, `activity`, `goal`), живут только
  в кэше и действуют до следующей правки;
- «Вернуть данные приложения» чистит кэш и возвращает экран к профилю хоста;
- ключ живёт отдельно от хранилища курсов (`wfpb_daily_`, `wfpb_system_keys_`),
  поэтому перезапуск курса его не стирает;
- доступ к хранилище идёт через `globalThis.localStorage` в try/catch: приватный
  режим и заблокированные хранилища не ломают экран, кэш просто отключается.

В стор приложения модуль не пишет по-прежнему.

## Что модуль не делает

- не ходит в сеть; из хранилища трогает ровно один свой ключ —
  `calculators.profile.v1` (см. «Личные данные и кэш»), чужие записи не читает и
  не удаляет; расчёт выполняется на устройстве;
- не добавляет глобальных стилей, шрифтов и `@font-face` (заголовок использует
  шрифтовой стек приложения, цвета — локальные CSS-переменные `.calc-screen`);
- не трогает стор, роутер и Telegram-клиент хоста;
- не грузит картинки извне: все 25 миниатюр лежат в `images/` и бандлятся вместе
  с модулем, путей в `public/` или CDN модуль не использует.

## Проверка

```bash
npx tsc --noEmit -p tsconfig.json     # без ошибок в src/modules/calculators
npx vitest run src/modules/calculators
```

Тестам нужны dev-зависимости, которых в приложении пока нет:
`vitest`, `@testing-library/react`, `@testing-library/jest-dom`, `jsdom`,
`@vitejs/plugin-react`. Если ставить их не нужно, исключите тесты из сборки:

```jsonc
// tsconfig.json
"exclude": ["src/modules/calculators/__tests__"]
```

Сам `pnpm tsc --noEmit` в приложении падает на `scripts/enrich_*.ts` до всякого
модуля — это устаревший Prisma-клиент, лечится `pnpm db:generate`.

## Как готовился модуль

Папка написана заново на основе исходного Manus-шаблона: из него не перенесены
ни рантайм-обвязка (`vite-plugin-manus-runtime`, `__manus__/`, debug-collector,
umami, `.project-config.json`), ни mёртвый UI-слой (shadcn/Radix, 6 189 строк),
ни роутер, ни моки профиля и заглушки API. Из шаблона взяты каталог калькуляторов,
формулы и тексты — и переписаны так, чтобы считать по профилю из пропсов.

Миниатюры сжаты до 192px по длинной стороне (`webp`, quality 90, alphaQuality
100, effort 6): 2.31 МБ → 0.47 МБ, −79.5%. Отклонение от оригинала считалось по
всем 25 картинкам в premultiplied RGBA на совпадающих размерах: в реальном
ренере 40px средний |Δ| по каналу 2.4–7.0 из 255 (худший кадр `14.webp` — 7.04,
единичный пиксель расходится на 38), на 120px (3× DPR) — до 11.67 (худший
`17.webp`). Вариант 144px (0.47 → 0.31 МБ) отклонён: на кратных DPR отклонения
растут до 15.29. Прозрачность сохранена у всех 25 (`alphaQuality 100`), «шахматки»
в исходниках нет — 17–20 взяты уже заменёнными.
